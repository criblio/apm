## Failure-mode taxonomy

The 11 below-perfect scenarios cluster into 4 root causes:

### A. Alert state machine doesn't reach FIRING for many error_rate scenarios

**Affected**: cartFailure (state never fires), failedReadinessProbe
(checkout never fires), llmRateLimitError (product-reviews never
fires), recommendationCacheFailure (recommendation never fires),
adFailure (ad never fires in 8min eval window).

**Hypothesis**: the home_service_summary scheduled search runs over
a -1h window. A 7-min flag-on burst on a low-traffic service
produces ~7 errors over ~70 calls in that window — but those 7
errors land in the same -1h that contains ~600 healthy calls from
the prior 53 minutes. The diluted error rate is right at or below
the 1% threshold `curr_err_pct >= 1`. The state machine then
needs FIRE_AFTER=2 consecutive bad cycles (10 min minimum) to
reach FIRING, which exceeds the eval's 8-min KQL assertion timeout
even for services that do clear the threshold eventually.

cartFailure should NOT have this dilution problem (cart is a
high-traffic service), but its state still never fired. Worth
verifying whether the cart flag is actually injecting errors in
this cluster — could be that `cartFailure=on` doesn't take effect
without an explicit pod-bounce in this otel-demo install.

### B. Alert pipeline → UI render path

**Affected**: productCatalogFailure shows alert state firing in
`$vt_results` AND alertHistory event landed in the otel dataset,
but `overviewDetectedIssuesproductcatalog`, `alertsPageproductcatalogFiring`,
and `svcDetailAlertBadge` all timed out. The data is there; the UI
isn't showing it.

paymentFailure shows alert state firing AND every UI surface
reading from `$vt_results` passes, but
`alertHistoryPaymentFired` (the otel-dataset history events)
never appears. The alert_history_send search isn't reliably
emitting transitions even though the state machine reaches FIRING.

These are separate-bug symptoms of one underlying area: the
fan-out from "state machine fires" → "every surface that should
react to it" is leaky.

### C. Investigator times out on gradual-onset scenarios

**Affected**: emailMemoryLeak (memory drift over hours),
leakFingerprint (multi-day cardinality climb),
recommendationCacheFailure (intermittent cache misses).

**Hypothesis**: the 5-min Investigator wait isn't enough for
scenarios whose playbook requires multiple sequential queries
(pod uptime + cardinality + error slope + downstream-health).
The Investigator returns no conclusion in the window so the eval
scores it 0 even though it would have found the root cause given
more time.

emailMemoryLeak in particular is a regression — surface detection
landed strongly (7/7) while investigator went from likely-pass
(unclear in April baseline) to timed-out.

### D. Surface contracts don't match observed cluster behavior

- **adHighCpu**: `homeAdP99Value` matches `[5-9](\.\d+)?\s*ms|...`
  Pattern. The ad service's adHighCpu impact shifts p95 from
  ~1ms baseline to ~3-4ms — below the 5ms minimum the pattern
  requires.
- **llmRateLimitError**: product-reviews drops off the Services
  list when its traffic is low enough; the eval's "navigate to
  serviceDetail" step then fails outright. Affects 2 surfaces.
- **failedReadinessProbe**: the flag is supposed to make k8s yank
  cart from the Service endpoints. checkout's upstream calls
  should fail. In this cluster the propagation doesn't happen
  reliably enough to cross even our most lenient error chip
  threshold. Could be a cluster-config issue or the flag's mech
  doesn't apply here.

## Investigator wins

Even though the surfaces are leaky, the Investigator scored
root-cause-correct on **10 of 11 scenarios** where it ran:
adFailure, adHighCpu, adManualGc, cartFailure, failedReadinessProbe,
kafkaQueueProblems, llmRateLimitError, paymentFailure,
paymentUnreachable, productCatalogFailure. The diagnosis layer is
strong; the detection layer is what needs work.

The three losses are emailMemoryLeak / leakFingerprint /
recommendationCacheFailure, all due to timeouts rather than wrong
conclusions — addressable with a wait-time bump or playbook
optimization.
